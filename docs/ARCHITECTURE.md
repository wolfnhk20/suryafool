# Suryafool — Bootstrap / Environment Agent

**Module:** `/bootstrap`
**Status:** Design spec for implementation
**Depends on:** deepagents, provider router (NIM/Groq/Gemini)
**Used by:** nothing (this runs first, standalone)

---

## 1. Purpose

Before any Suryafool mission agent can run, the host machine needs a working
toolchain: WSL2, a Linux distro, USB passthrough, packet-capture tools,
Python dependencies. Setting this up today is a manual, iterative
"run command → read error → fix → retry" loop.

This is the same shape as a **Diagnose mission** (see main PRD, Section 8.5),
pointed at the dev environment instead of a wireless environment:

```
DISCOVER → OBSERVE → COMPARE → HYPOTHESIZE → REMEDIATE → VERIFY
```

The Bootstrap Agent automates this loop so the team (and eventually any
user) can run one command and have their environment brought up to spec.

---

## 2. Critical design rule

**This agent is not a Suryafool mission agent and must not share trust
tiers with one.**

Mission agents (Discovery, Correlation, Security Research, etc.) operate on
wireless capability data and are gated by **Scope Guardian**, which reasons
about wireless targets and authorization scope.

The Bootstrap Agent operates with **OS-level access** on the user's own
machine (installing packages, enabling WSL features, sometimes requiring
admin/sudo). That is a fundamentally different risk category. It gets its
own gate, described below, and lives in its own module (`/bootstrap`, not
`/agents` or `/scope-guardian`).

**The LLM's job is diagnosis and interpretation — not command generation.**
Every command that can mutate the system comes from a fixed, human-reviewed
manifest. The model never freehands a shell command it invented itself.

## 4. Dependency manifest

Ground truth for what "ready" means. Human-authored and version-controlled,
never generated by the LLM at runtime.

```yaml
- name: wsl-ubuntu
  check_cmd: "wsl -l -v"
  expect_contains: "Ubuntu"
  install_cmd: "wsl --install -d Ubuntu"
  requires_elevation: true

- name: usbipd
  check_cmd: "usbipd list"
  expect_exit_code: 0
  install_cmd: "winget install usbipd"
  requires_elevation: true

- name: aircrack-ng
  check_cmd: "wsl -d Ubuntu -- which airmon-ng"
  expect_exit_code: 0
  install_cmd: "wsl -d Ubuntu -- sudo apt install -y aircrack-ng"
  requires_elevation: true

- name: usb-passthrough
  check_cmd: "wsl -d Ubuntu -- lsusb"
  expect_contains: "<adapter VID:PID>"
  install_cmd: "usbipd attach --wsl Ubuntu --busid <BUSID>"
  requires_elevation: false
  depends_on: [wsl-ubuntu, usbipd]

- name: python-deps
  check_cmd: "wsl -d Ubuntu -- python3 -c 'import scapy, deepagents'"
  expect_exit_code: 0
  install_cmd: "wsl -d Ubuntu -- pip install scapy deepagents --break-system-packages"
  requires_elevation: false
```

Each entry:
- `check_cmd` — read-only, always safe to run without gating.
- `expect_contains` / `expect_exit_code` — how the agent decides pass/fail.
- `install_cmd` — the *only* remediation the agent is allowed to run for
  this dependency. Not model-generated.
- `requires_elevation` — if true, always pauses for human confirmation,
  every run, not just the first.
- `depends_on` — ordering constraint (e.g. USB passthrough needs WSL +
  usbipd present first).

## 5. Agent responsibilities (what the LLM actually does)

The model is good at exactly the parts that are messy and unstructured:

- Parsing noisy check-command output (e.g. distinguishing `docker-desktop`
  from `Ubuntu` in `wsl -l -v` text).
- Deciding dependency order when a check fails in an unexpected way.
- Explaining to the user, in plain language, what's missing and why.
- Selecting *which* manifest entry's `install_cmd` to propose next.
- Re-running `check_cmd` after remediation and confirming success.
- Producing a final "environment ready" / "environment blocked, here's why"
  report.

The model does **not**:
- Invent or edit shell commands.
- Run anything with `requires_elevation: true` without an explicit human
  confirmation shown alongside the exact command.
- Modify the manifest itself.

---

## 6. Provisioning Guardian

A small deterministic gate, analogous to Scope Guardian but scoped to
system provisioning instead of wireless targets:

- Any manifest entry with `requires_elevation: true` → **always** pauses
  and shows the user the literal command before executing.
- Any manifest entry with `requires_elevation: false` → may run
  automatically (e.g. re-running a read-only check, or a passthrough
  command that doesn't touch system state).
- The agent cannot bypass this by rephrasing intent — the gate keys off
  the manifest entry, not the model's stated justification.

This is the safety line worth stating explicitly in the report: *the
provisioning agent can diagnose and propose fixes autonomously, but never
executes privileged system changes without explicit human confirmation.*

## 7. Tool interface (for implementation)

```python
def check(dependency_name: str) -> CheckResult:
    """Run a manifest entry's check_cmd, return pass/fail + raw output."""

def propose_remediation(dependency_name: str) -> RemediationProposal:
    """Look up the manifest's install_cmd for a failed dependency.
    Does not execute anything."""

def request_elevation(proposal: RemediationProposal) -> bool:
    """Show the exact command to the human, block until approved/denied.
    Always invoked when requires_elevation is true."""

def remediate(dependency_name: str) -> RemediationResult:
    """Execute the manifest's install_cmd. Only callable after
    request_elevation() has returned True, if required."""

def verify(dependency_name: str) -> CheckResult:
    """Re-run check() after remediation to confirm success."""
```

The Bootstrap Agent's loop, in plain terms:

1. Run `check()` for every manifest entry in dependency order.
2. For each failure, call `propose_remediation()`.
3. If `requires_elevation`, call `request_elevation()` and stop if denied.
4. Call `remediate()`.
5. Call `verify()`. If still failing, report the raw output back to the
   user rather than retrying blindly — don't loop silently on a genuine
   failure.
6. When all entries pass, report "environment ready" and hand off to the
   Mission Orchestrator.

## 8. Where this lives

```
/bootstrap
  manifest.yaml           # the dependency manifest above
  checks.py                # check() implementations per dependency
  remediate.py              # remediate() implementations per dependency
  provisioning_guardian.py  # the elevation gate
  agent.py                  # the deepagent wiring these tools together
```

Invoked standalone, e.g. `suryafool doctor`, at setup time or on-demand —
not invoked mid-mission by any of the 12 wireless agents.
